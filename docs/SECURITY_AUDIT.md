# Zero One DAO — pre-mainnet security audit

Branch `security-audit` (from `main` @ 5d6f97b), audited 2026-09-09 on a local anvil devnet against the mirror deployment
(`scenarios/lib.ts` / `scripts/deploy-local.ts`). Nothing touched a public network. Tests and logs live under `evidence/audit/`
(`governance-nav/`, `work-templates/`, `account-relay/`, `ops-economic/`); every path in this document is relative to the repo root.

Method: four component reviewers (governance + NAV, work + templates, account + relay, operations + economics) produced the rows;
one independent reviewer then re-ran every Critical / High test and tried to refute each such row. Severities below are the
severities **after** that refutation pass; the original severity is noted where it changed. One row (ECO-01) was refuted and
moved to Appendix A. Nothing was fixed; the design authority (Fable) decides.

Severity meaning: **Critical** = the DAO or its treasury is lost for the cost of gas; **High** = members lose funds or the DAO
loses liveness against an actor who neither out-votes nor out-waits them; **Medium** = bounded loss, or loss that requires an
already-accepted precondition plus one more; **Low** = holds, or misreport / delay only; **Accepted-by-principle** = the
constitution explicitly allows it *and* vote or exit protects the loser (each such row says how).

## (b) Accepted by principle

Each row is accepted only because the constitution explicitly allows the action **and** vote or exit actually protects the loser:

- **GOV-07** (1 s / 1 s and uint32-overflow Config): any parameter is changeable by proposal; after the lock every member still ragequits at full pro-rata (C paid 1000 USDC for 1000 shares in t10). The loss is the DAO's ability to decide, never the money. Must-document the overflow variant.
- **GOV-09** (proposals that add Safe owners/modules, set shamans, flip locks): PARAMETERS.md already states it is a vote. Protection exists for exactly the 12 h window: the decoded calls show `enableModule` / `setShamans` targets, a NO majority defeats it, and any member exits at NAV before execution. There is no protection afterwards — the README must say these proposals are one-way. Fable should weigh this against GOV-02 / GOV-03, which shrink the effective window to "NO > 51.5% within 6 h".
- **W-3** (verifier = proposer's second key): verifier list, threshold and reward are in the voted proposal; a member who does not trust them votes NO or exits in grace at full NAV; quorum 0 makes silence the member's own choice. The code rule `verifier != proposer` buys no security and the docs should stop presenting it as protection.
- **T-13** (migrate to a hostile successor, amend to absurd bounds): the successor address, code hash and new Rule are the content of the vote; 6 h grace exit at NAV of the Safe; > 34% exits defeat it. Caveat: the raw holdings being migrated sit outside the Safe, so exit during that vote pays Safe pro-rata only (NAV-05).
- **A5-18** (re-delegating the EOA to hostile code resets the nonce): equivalent to giving away the key; nobody else is harmed; the constitution cannot govern self-surrendered control.
- **ECO-02** (sleeping members): silence is consent by design; exit is available at NAV every block of the 12 h window. Real only while the window is 12 h (ECO-04) and the treasury is in the Safe (ECO-08 / NAV-05).
- **ECO-01** (large depositor captures a small treasury; refuted as a High finding, Appendix A): the objector who exits in grace loses nothing (C in T06); being out-voted and choosing not to exit is majority rule.

Explicitly **not** accepted by principle although documented: **OPS-05** (Circle blacklist of the Safe — vote and exit protect nobody; PARAMETERS records it as "the user's choice", so it is an accepted counterparty risk that must be disclosed), **A5-07** (operator can sign for every T0 account — a custody trade-off, not a constitutional one), and **NAV-05 / ECO-08** (exit forfeits the deployed fraction — a phase-4 ruling, not a principle; exit does not protect the loser while capital is out).

## (c) Where phase 4 (TreasuryLedger, TWAP) is insufficient or introduces a new failure mode

The phase-4 code (branch `phase4-ledger-twap`) is not in this checkout, on any local branch, or on origin; everything below is
argued from decision.md phase 4 and goals/phase4-ledger-twap.md and must be re-tested once the branch exists.

**Ledger — insufficient:**
1. **W-1**: the ledger counts USDC on open instances, not share liabilities. Approved-but-unminted task rewards (no expiry) still dilute later depositors by up to the voted reward (−41.2% on 10,000 USDC in the test).
2. **NAV-02**: the empty-treasury rule keys on `treasury == 0`, not `supply == 0`; Safe 0 + open instances 0 with shares outstanding still re-prices every share to 1 USDC (depositor −75.3%). The ruling text ("when totalShares == 0") does not match the code condition.
3. **NAV-08 / NAV-06**: committed-but-unpaid amounts (Project tranches to an operator, Ready-forever Payments) are counted at face, so the depositor overpays by its pro-rata of those (246.9 of 1000; 1242.24 of 5000). Consistent with "exit price ≤ deposit price" but the depositor is the loser with no vote.
4. **NAV-05 / ECO-08**: ragequit stays Safe-only by ruling, so exit is most expensive exactly when the DAO is doing something (98.4% forfeited with 3000/3050 deployed; 65.57% with a 2000 Project). Composed with GOV-02 / GOV-03 the only remedy left is out-voting within 6 h.
5. **GOV-02**: the phase-4 "Voting" section's cost model ("attacker capital exposed during grace") is false — exposure is 2 blocks. The ledger changes nothing here.
